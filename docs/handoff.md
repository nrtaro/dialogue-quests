# AI対話型ミッションゲーム全体：Codex開発引継ぎ・初回依頼

この文書を、GitHubリポジトリに接続したCodexの最初の依頼として読んでください。
あなたには、以下の方針で、ブラウザで実際に遊べる、複数コンテンツを収録するAI対話型ミッションゲーム全体を、段階的に完成させてもらいます。「勇者の耳元」はゲーム全体の名称ではなく、共通の体験と仕組みを検証するための最初のコンテンツです。初回実装ではこの1本を遊べるようにし、そのプレイ記録から全コンテンツに通じる細部を調整した後、コンテンツを追加します。まずリポジトリと実行環境を調べ、リポジトリの推奨設定と必要な手順を説明し、その後、実装と動作確認まで進めてください。単なる企画書や固定会話の再生で終わらせないでください。

## 1. 目的と決定事項

- 一人用、PC・スマートフォンのブラウザ対応。初期利用者は約5人。
- 共通の会話UIで、目的の異なる短いTRPG風ミッションを遊べるゲームを目指す。
- ゲーム全体の名称は未決。特定の舞台・登場人物を全体名や共通仕様にしない。
- 最初の検証コンテンツは「勇者の耳元」。1プレイ5〜10分程度を目安とする。
- このコンテンツに限り、プレイヤーはナビ妖精となり、自由な文章で質問・助言し、AI勇者が判断して行動する。
- 全体では、プレイヤーの立場や対話相手、目的、制約が異なるミッションを同じ操作・画面の枠組みで遊ぶ。勇者への助言は、その遊び方の一例。
- プロジェクトの到達点は、コンテンツ選択から対話・結果・再挑戦まで成立し、検証後に複数コンテンツを追加できるゲーム全体の完成。初回デモ完成とは区別する。
- AI出力はテキストと構造化データのみ。生成画像、生成音声、新しい素材の自動追加は不要。
- 生成内容が変わっても同じ画面部品で表示できる設計にする。
- 最初から仕様を固め切らず、遊べるデモとプレイ記録を使って改良する。
- 本文中の具体的なシナリオ値や内部構成は初期案。確定事項と実装上の提案を区別する。

## 2. 最初に行うこと：リポジトリと環境の確認

既存のAGENTS.md、README、コード、依存関係、git状態、リモート、利用可能な実行コマンドを確認する。既存コードや未コミット変更を上書きしない。認証済みの操作範囲を確認し、できる操作とユーザーが行う操作を区別する。秘密情報の値を表示しない。

リポジトリが未作成なら、推奨の仮名は dialogue-quests（ゲーム正式名は未決）、最初はPrivateを推奨。ユーザーが作成する前提で手順を説明し、作成済みなら二重作成しない。既にhero-whisper等の名前で作成済みでも、無断で改名・再作成しない。名称と説明を全体方針へ変更する案を示し、既存の接続を尊重する。GitHubの状態を確認できなければ未確認と明記する。

## 3. リポジトリ設定を必ず説明する

初回報告で次の項目について「推奨設定／理由／現在の確認結果／操作場所または必要な手順」を表にする。GitHubやCodexの最新UI・プラン制限は確認できる公式情報で検証し、推測の画面名や利用できない機能を断定しない。

- リポジトリ名・説明・公開範囲：初期はPrivate。公開変更は別途の判断。
- 初期化：README、適切な.gitignore。作成画面での初期化とローカル初期化を重複させない。
- ライセンス：配布方針が未決なので無断で選ばない。Privateでもライセンスの検討は別項目として説明。
- デフォルトブランチ：main。作業は feature/mission-game-demo などのブランチを使い、PRで確認可能にする。現在の作業環境に合わせ、不要なworktreeは作らない。
- mainの保護：force push・削除の制限、可能ならCI必須。個人開発で行き詰まる必須の他者承認は設定しない。Privateでの利用可否とプラン制限を確認し、使えない場合も開発を止めない。
- Issues：バグ・改善・検証結果の記録。大きなProjects運用は初期に不要。
- GitHub Actions：lint、型確認、主要テスト、ビルド。最低限の権限にする。
- 秘密情報：ローカルの.env.local等とデプロイ先の環境変数を区別。GitHub Actions SecretsはCIで本当に必要な場合だけ。通常CIは実APIキーなしで動くようにする。
- Codex：対象リポジトリの接続、作業環境、依存関係の導入、秘密情報の渡し方、ネットワーク制限を確認。GitHubのSecretsがCodexへ自動的に渡ると仮定しない。
- .gitignore：環境変数ファイル、node_modules、ビルド出力、個人のプレイ記録等を除外。.env.exampleはダミー値だけをコミット。
- AGENTS.md：開発・検証コマンド、ゲーム設計上の不変条件、秘密情報の扱い、記録更新先を簡潔に残す。
- GitHub Pages：APIキーを安全に保持するサーバーの代わりにはならない。画面だけの公開と、サーバーを含む公開を混同しない。

権限・プランの都合で未適用の設定は、適用済みと報告しない。設定の説明だけで作業を終わらせず、接続済み環境で可能なローカル実装を進める。公開範囲変更、課金契約、一般公開、mainへのマージは勝手に行わない。

## 4. 推奨技術

React＋TypeScriptを採用する。ReactはゲームエンジンではなくUIライブラリだが、本作は文章とフォーム中心なので適している。

新規リポジトリならNext.js＋TypeScriptを第一候補とし、画面とサーバーAPIを一つのプロジェクトにまとめる。既存構成がある場合は合理的に再利用する。バージョンは実装時の安定版・実行環境との互換性を確認し、lockfileを保存する。

AIは既存APIの安価な文章モデルを想定。GPT-6 Luna等のモデル名・アクセス可否・API仕様・料金は実装時に公式情報で確認する。モデル名を環境変数で切り替えられるようにする。特定モデルへのアクセスを前提にして実装を止めない。

APIキーをブラウザへ渡さない。NEXT_PUBLIC_等の公開環境変数に秘密を置かない。DBやアカウント機能は最初から大きく作らず、まず1セッションの正常な進行を優先する。

## 5. ゲーム全体のゲーム性とコンテンツの分離

全体の核は「明確な目的を持つ短い状況で、自由な対話を使って情報・人物の判断・出来事へ働きかけ、結果へ至る」こと。全コンテンツを、助言で相棒を導く遊びに限定しない。交渉、調査、説明、調整なども扱える余地を残すが、追加する内容は共通体験を調整した後にユーザーと選ぶ。

共通部分：コンテンツ一覧、概要と目的の確認、セッション開始、対話入力、状況・状態の表示、行動や結果の反映、終了判定、振り返り、再挑戦、一覧へ戻る、ログ出力、AI接続・エラー対応。

コンテンツ固有部分：舞台、プレイヤーの役割、登場人物、人物の知識と性格、初期状態、公開／非公開情報、行動・効果、時間や資源の規則、達成／失敗条件、開始文と結末。

「勇者の耳元」では、プレイヤーが情報を集め、助言し、結果に合わせて方法を変える。勇者は性格・経験・観察に基づいて判断する。以下の原則は相手が勇者以外でも適用できるようにする。

- 助言に必ず従うだけにも、気まぐれに反抗するだけにもしない。
- 拒否や別案には、プレイヤーが理解できる短い理由を付ける。
- 質問しないと重要情報が一切出ない設計を避け、勇者も必要に応じて自発的に報告する。
- AIが全解法を先に説明しない。プレイヤーに考える余地を残す。
- 正解の言い回しを当てるゲームにしない。同じ意図の言い換えや代案を受け止める。
- 失敗は因果のある結果にし、可能なら旅を継続させる。
- シナリオの事実を、プレイヤーの「既に入手したことにして」等の発言だけで改変しない。

## 6. 初回検証コンテンツ「勇者の耳元」の初期シナリオ「日没までの帰り道」

目的：月白草を入手し、日没までに勇者リオを村へ帰還させる。

初期状態：残り45分。リオは軽い足のけががあり、歩けるが走れない。持ち物は剣・包帯・干し肉1個・着用中の上着。リオは人助けを優先し、自分のけがを軽く考える。妖精は物に触れず、近くの魔力を感知できるが、物理的危険は自動で分からない。

場面の初期案：
1. 分かれ道：傷んだ吊り橋は片道8分。川沿いは片道14分。調査・迂回・危険を承知で進む等の選択がある。
2. 祠の入口：親獣が子獣を守っている。観察、餌による誘導、待機、追い払う等の方法を検討できる。
3. 月白草：台座の魔力線が灯具につながる。「採る者は、先に灯を伏せよ」という手掛かりがある。灯具を覆う方法、道具の使い道などを考える。
4. 帰路：足の状態、包帯、残り時間、利用できる経路が結果に影響する。

この場面構成や数値はゲーム調整用の初期案で、固定された成功会話ではない。場所の距離、道具、所要時間、罠の効果、負傷と移動時間の関係は、実装前に整合するルール表にする。前の場面で未入手の道具を突然出したり、失敗させるために隠し条件を追加したりしない。

短い会話や質問では原則時間を減らさず、観察・移動・作業に時間を設定する。無限の質問が必要になる場合は、いきなり全発言へ時間ペナルティを付けず、プレイ結果を見て調整する。

## 7. AIと状態管理の境界

ゲーム側がコンテンツごとの状態と達成条件を管理する。「勇者の耳元」では現在地、時間、負傷、持ち物、発見済み情報などを持つが、これらを全コンテンツの必須項目にしない。AIは登場人物の発言と、許可された範囲の行動・進行の提案を返す。

- 構造化出力はスキーマで検証する。
- 行動の前提条件、コスト、効果をゲーム側で確認し、原子的に適用する。
- 会話の描写と状態更新を一致させる。失敗した行動を成功した文章で表示しない。
- 同時送信・再試行で時間や道具を二重消費しない。
- クライアントから送った状態を無検証で正本にしない。デモでもサーバー側のセッション管理など、一貫性の保てる簡素な方法を選ぶ。
- 未想定の提案は、対応可能な行動への解釈や代案として扱う。未知の効果を無検証で追加しない。
- 本当に自由な行動の追加は将来検討。初期デモの対応範囲は明記する。
- AI出力エラー、通信失敗、タイムアウトでは状態を壊さず再試行できるようにする。

人格応答・進行・状態管理は責任を分けるが、毎ターン複数モデルを呼ぶことまでは要求しない。呼び出し回数を抑える。

## 8. 共通画面とログ

初回から「コンテンツ一覧→概要・役割・目的の確認→プレイ→結果→再挑戦／一覧へ戻る」の導線を実装する。実在する選択肢は初回コンテンツ1本でよい。未実装コンテンツを遊べるように見せない。

プレイ画面は目的、必要な状態、会話履歴、プレイヤーだけの情報、入力欄、送信、任せる／進める操作、リセット、終了結果、ログ出力を共通部品として実装する。残り時間や負傷表示は、そのコンテンツが必要とする場合だけ表示する。「勇者に任せる」などの文言はコンテンツ設定から与える。読みやすさを優先し、スマホのキーボード表示でも入力欄が使えるようにする。長文・長い単語・連続送信・日本語変換中のEnterを考慮する。

会話を状況説明・登場人物・プレイヤー・行動結果で視覚的に区別する。表示名を勇者／妖精で固定せず、コンテンツ定義から設定する。返信待ちとエラーを明示する。AIの未検証HTMLをそのまま描画しない。

プレイ記録はJSONを基本に、人が読めるテキストも出力できるとよい。記録項目：共通システムの版、コンテンツID、シナリオとルールの版、モデル識別子、セッションID、発言、確定行動、状態の前後、経過時間、終了理由、API使用量・応答時間（取得できる範囲）。秘密情報やモデルの非公開思考過程は記録しない。個人の実プレイログは既定でGit管理しない。

## 9. 追加と調整を支える最小限の構成

コンテンツ定義を共通UI・API呼び出し・セッション管理から分離する。例えば src/game/ を共通進行、src/content/hero-whisper/ を初回コンテンツ、src/content/registry.ts を登録一覧とする。実際のディレクトリはフレームワークに合わせてよい。

定義にはID・版・タイトル・概要・プレイヤー役・登場人物・初期状態・表示する状態項目・ルール・終了判定を持たせる。台詞や勇者固有のルールを共通APIや画面へ散在させない。複雑なルールは型付きのコンテンツ別処理でもよく、万能なJSON形式やノーコード編集画面を先に作らない。

別の最小テスト用コンテンツ定義で、名前・目的・状態項目・終了条件を差し替えても共通画面が動くことを確認する。これは一般公開する第2コンテンツの制作ではなく、勇者専用の構造になっていないかの内部確認とする。

改善記録は「共通システム」「コンテンツ固有」「要検証」に分ける。入力、文章量、待ち時間、情報の見せ方、判定の納得感など共通の問題は、勇者用の特例で隠さず共通部分へ反映する。修正後は共通の回帰確認と初回コンテンツの整合性確認を行う。

## 10. 実装と検証の順序

1. 環境確認、リポジトリ設定の説明、初期仕様と未決事項の整理。
2. 短い設計・作業計画をリポジトリへ保存し、シナリオのルール表を作る。既に示した目的の再ヒアリングは不要。
3. コンテンツ登録、一覧・開始・プレイ・結果の共通導線、状態管理と画面を作る。接続前は明確にモック表示とする。
4. サーバーから実AIへ接続し、自由入力で開始から終了まで遊べるようにする。
5. 主要なルール、状態更新、二重送信、出力検証、失敗時の処理を検証。外部APIなしでCIを実行できるようにする。
6. 実APIで短い動作確認を行う。キーがない場合はその部分のみ未確認として、ユーザーが安全に設定する場所と実行手順を示す。モックを実AI接続済みと報告しない。
7. 慎重な助言／大まかに任せる／未想定の提案、の3方針でプレイし、状態の整合性と展開差を比較する。
8. ユーザーが実際にデモを遊び、細かな修正を繰り返せる状態で提示する。模擬プレイだけで体験の承認を得たことにしない。
9. フィードバックを共通／固有へ仕分け、修正・再プレイを繰り返す。調整を待たずに大量のコンテンツ制作へ進まない。
10. 共通体験についてユーザーが次へ進むと判断したら、第2コンテンツを選び、同じ基盤へ追加する。目的や対話の役割が異なる内容で拡張性を検証する。
11. 複数コンテンツで共通UI・進行・品質を再確認し、小規模利用に必要な運用を整えてゲーム全体の完成へ進める。

各段階でブランチとPRまたは差分をレビュー可能にし、起動方法と確認結果を報告する。初回の開発依頼は1〜8を実装・検証すること。9以降は実プレイのフィードバックを受けて進める。

## 11. 初回デモの完成条件と提出内容

- PCとスマホ相当の表示で、コンテンツ選択から開始・入力・結末・再挑戦／一覧へ戻るまで進められる。
- 共通システムとコンテンツ定義が分離され、差し替え確認で勇者固有の必須項目がないことを確認できる。
- 実AIに自由入力でき、勇者が発言と行動を返す。
- 助言によって行動や結果が変わることを記録で確認できる。
- 持ち物、時間、場所、負傷、文章の間に矛盾がない。
- 勝敗が登場人物の自己申告だけで決まらない。
- 再挑戦とログ出力ができる。
- lint、型確認、必要なテスト、ビルドの実施結果を報告する。未実施は未実施と明記。
- READMEに導入、環境変数、起動、検証、既知の制約を記載する。
- 最終報告に、変更内容、起動URLまたはコマンド、実AI接続の確認状況、リポジトリ設定の適用済み／手動操作待ち、既知の問題を示す。

## 12. プロジェクト全体の完成との区別

初回デモの完了は、プロジェクト全体の完了ではない。全体の目標は、調整済みの共通体験の上で、役割・目的・状況が異なる複数コンテンツを選んで遊べるゲームを完成させること。

全体完成の条件は、複数コンテンツで共通導線が成立し、対話と状態・結果が整合し、再挑戦や記録が使え、小規模利用に必要なAPI利用制限・費用把握・エラー対応・アクセス管理が整っていること。収録本数、正式タイトル、公開先、公開範囲、最終的な品質基準は実プレイ調整後にユーザーと確定する。

最初に「勇者の耳元」を使う理由は、実際のプレイを通じてゲーム全体の共通部分を細かく調整するため。勇者専用ゲームを完成させてから別ゲームへ作り直す進め方にはしない。一方、将来対応のための過剰な汎用化もしない。小さく遊べる全体構造を作り、実プレイで磨き、その後にコンテンツを増やす。
