# 無料AIで品質を保つための設計

2026-11-04 / Claude Code。ユーザー指定（回答27）：無料AIのみで実装する。そのうえで、次の3点の質にこだわる。

- 自由な展開
- クリアと失敗の境界
- 過程に応じた講評

以下は設計の提案で、効果は試作と判定試験で確かめる。

## 基本の考え方

**AIには「言葉を読む・言葉を書く」だけを、小さく区切って任せる。面白さ・公平さ・事実は、ゲームの定義とルールで作る。**

無料のモデル（Gemma等）は、上位の有料モデルより、長い文脈・暗黙の推論・事実の保持で間違えやすい。前回のGemma試験の失敗（真相の書き換え、人物の取り違え、ないセンサーの追加）は、どれも「AIに長い話と事実を同時に任せた」ことから起きている。逆に、短く範囲の決まった仕事（分類・抜き出し・短い文章）なら十分戦える。

## 1. 自由な展開を保つ工夫

| 工夫 | 内容 | どこで |
|---|---|---|
| 1-1 仕組みの共通の型 | プレイヤーの新しい案を、共通の「仕組みカード」（§1-A）へ写す。案の中身は自由でも、AIが埋めるのは決まった欄と少数の作用の種類なので、間違えにくい | 定義（ゲームごと）＋コード（共通） |
| 1-2 汎用の「印」 | 物や人物に、プレイヤーが言葉で印を付けられるようにする（例：「月曜の物」「赤い付箋の物」）。印は状態として保存し、仕組みの条件に使える。レビュー指摘R2への対応 | コード |
| 1-3 誤解の型 | 意外な解釈を、決まった台詞の表ではなく「誤解の型」で定義する（§1-B）。中身はその場の物と言葉から作るので、同じ笑いの繰り返しを避ける | 定義 |
| 1-4 迷ったら確認 | AIの解釈とキーワード処理の解釈が食い違ったら、勝手に決めずに確認を返す。確認は人物の台詞として、口語だけで言う（§1-C） | コード |

### 1-A 仕組みカード

プレイヤーの案は、次の欄を持つカードへ変換する。AIが埋め、ルールが検査する。

| 欄 | 意味 | 例（31 掃除ロボ） | 例（19 避難訓練） |
|---|---|---|---|
| 名前 | プレイヤーの言葉を短く | 迷ったら保留 | 無言の見守り当番 |
| 担い手 | 誰が動くか | ロボ | 係員 |
| 対象 | 何に・誰に働くか（下の選び方） | どの方針にも当たらない物 | 字が読めない住民 |
| きっかけ | いつ働くか | ずっと（物を見るたび） | 各ラウンドの始め |
| 作用 | 何が変わるか（下の作用の種類から1つ） | 移す → 保留箱 | 伝える → 手を引いて出口へ |
| 費用 | 何を使うか | 1動作 | 係員1人、1ラウンド |
| 使う物 | 補完の検査の対象 | 箱（自然な物） | なし |
| 期間 | 1回だけ／ずっと／N回まで | ずっと | 訓練の間ずっと |
| 優先 | ほかの仕組みとぶつかった時 | 新しい方が先（言葉で「何より先に」と言えば最優先） | 同左 |

**対象の選び方（共通）：** 印（例：書き込みあり）、名前（例：手紙）、場所（例：床の上）、状態（例：濡れている）、「どれにも当たらない物」。これらを「かつ・または・ではない」で組み合わせられる。

**作用の種類（共通の一覧。各ゲームは使う物だけを有効にする）：**

| 作用 | 意味 | 主に使うゲーム |
|---|---|---|
| 移す | 物・人の置き場所や位置を変える | 31、01、19、勇者 |
| 変える | 印や状態の値を付ける・外す・増減する | 31、01、37 |
| 伝える | 合図・看板・字幕で、相手が知ることを変える | 19、25、勇者 |
| 頼む | 人物に行動を頼む（相手の意思で断られることがある） | 01、07、30、勇者 |
| 作る | 自然な物から、箱・役割・当番などを作る | 31、19、01 |
| 待たせる | 実行を保留する・順番を後にする | 31、19 |
| 確かめる | 調べる・聞く。情報が増えるだけで、状態は変えない | 07、31、勇者 |
| 決める | 規則（条件 → 許可・不許可）を作る | 13 |
| 書き換える | 文章の一部を変える | 37、25、30、48 |

**検査の順番：**

1. 対象が今の状態から選べるか。
2. 作用がそのゲームで有効か。
3. 使う物が補完の規則を満たすか。
4. 費用を払えるか。
5. 担い手にできることか（意思が必要なら、相手の事情で判定）。
6. 固定事実を変えないか。

どこで落ちたかを、そのまま人物の台詞の理由に使う。

### 1-B 誤解の型（繰り返しで退屈にしない）

ご指摘のとおり、決まった誤解の台詞を表にすると、2回目以降は読めてしまう。そこで、次の4点で設計する。

- **型で持つ：** 「文字どおりに受け取る」「範囲を広げすぎる」「主語・相手を取り違える」「優先順位を逆にする」「一度覚えたことを別の場面に当てはめすぎる」などの型だけを定義する。具体的な中身は、その時の言葉と部屋の物から作る。例えば「文字どおり」の型は、「持ち主」なら物本人への面談に、「きれいにして」なら物を磨き始めることになる。
- **プレイヤーの言葉で起こす：** 誤解は、プレイヤーの言葉にあいまいさがある時にだけ起きる。慣れたプレイヤーが正確に言えば起きない。これは上達そのもので、評価の「教え方」に反映される。
- **人物の性格を状況ごとに変える：** 新しい状況では、ロボの性格（文字どおり派、慎重すぎる派、張り切りすぎ派など）を変える。同じ言い方でも、起きる誤解が変わる。
- **AIに新しい誤解を提案させる：** 型の範囲内で、AIが新しい誤解を出してよい。状態への作用はルールが検査するので、矛盾は起きない。

それでも同じ型が続く場合に備え、直近の数プレイで使った型は出にくくする。

### 1-C 確認の言い方

「」の中は、人物が実際に話している口語だけで書く。番号・記号・箇条書きは使わない。

- 悪い例：「①家の人に聞く ②物本人に聞く、どっち？」
- よい例：「持ち主って、おうちの人のことですか？ それとも、この靴下さんご本人に聞けばいいですか？」

プレイヤーは普通の言葉で答える（「家の人」「本人に聞いて」など）。この規則は確認に限らず、人物の台詞すべてに適用する。システムの案内（画面の説明文）は「」の外に書き、台詞と混ぜない。
| 1-5 自然な物の一覧 | 補完できる物を、分類と例でゲームの定義に書く（台所なら布・容器・紙など）。AIの判断を「一覧に当てはまるか」に狭める | 定義 |

## 2. クリアと失敗の境界をはっきりさせる工夫

| 工夫 | 内容 | どこで |
|---|---|---|
| 2-1 達成条件は全部ルールで判定 | 掃除ロボと同じく、成功・失敗は状態から計算する。AIに「成功したか」を聞かない | コード |
| 2-2 条件と進み具合を常に見せる | 開始時に条件を示し、プレイ中は進み具合（守れる物の数、片付け率の見込み等）を出す。「なぜ失敗したか分からない」をなくす | 画面 |
| 2-3 失敗理由の因果をルールが書く | 本番の各手順に「どの方針で動いたか」を記録してある（`by`）。結果画面で「家族写真を捨てた ← 『汚れた物は捨てる』の思い込みが残っていた」と、ルールが正確に説明する | コード（一部実装済み） |
| 2-4 創作系はチェックリストで判定 | 30・48・13のように文章の質が絡むゲームは、AIに点数を付けさせない。「伏線Xは結末で使われたか？」のような**はい・いいえの質問**と、**本文からの引用**を返させる。引用が本文に実在するかをコードで確かめる。小さなモデルでも、はい・いいえは安定しやすい | 定義＋コード |
| 2-5 同じ記録なら同じ判定 | 判定に使う問いは温度などの揺れを抑えた設定で1回だけ行い、記録に保存する。採点し直しても結果が変わらないようにする | コード |

## 3. 講評の質を保つ工夫

| 工夫 | 内容 | どこで |
|---|---|---|
| 3-1 講評の材料はルールが選ぶ | 記録から、山場をルールで選んで「材料メモ」にする。山場の例：最初の誤解、立て直した手、一番大きな状態変化、失敗の原因、意外な出来事。AIには長い履歴を渡さず、このメモだけを渡す。事実の取り違えが起きにくくなり、無料枠の消費も減る | コード |
| 3-2 3人に別々の材料を割り当てる | 実用の人には失敗の原因、気持ちの人には守れた物、本人には誤解と修正、というようにルールで振り分ける。口調だけ違う同じ講評にならない | 定義＋コード |
| 3-3 人物カード | 各講評者に、立場・口癖・語尾・言い回しの例3つ・使わない言葉を定義する。小さなモデルは例を真似るのが得意 | 定義 |
| 3-4 ネタ帳との組合せ | 出来事の種類ごとに、設計者が面白い言い回しの例（ネタ帳）を用意する。AIはそれを今回の出来事に合わせて1文に直す。白紙から笑いを作らせない | 定義 |
| 3-5 出力の検査と定型への戻し | 物・人物の名前が記録にあるか、数字が記録と一致するか、長さ、禁止表現（「お話にならん」等の強すぎる言い方）を検査する。不合格なら、ネタ帳を使った定型の講評に戻す | コード |

## 4. AIの呼び出し方の工夫

| 工夫 | 内容 |
|---|---|
| 4-1 1回に1つの仕事 | 解釈・判定の質問・講評を別々の呼び出しにする。長い指示を1回にまとめない |
| 4-2 型と境界の例を見せる | 下の§4-A。アイデアを網羅するためではなく、仕組みカードの書き方と、受理・不受理の境界を示すために使う |
| 4-3 必要十分な文脈の束 | 下の§4-B。削るのは無関係な履歴や飾りで、つじつまの根拠は削らない |
| 4-4 明らかな操作はAIを呼ばない | 「本番へ」「ここまでで採点」、ゲームへの宣言、単純な定型文は、ルールだけで処理する |
| 4-5 解釈の再利用 | 同じゲームで同じ文面の入力は、前回の解釈を再利用する（よく使われる言い方ほど節約になる） |
| 4-6 仕事ごとにモデルを選ぶ | 同じ無料枠の中で、分類は軽いモデル、講評は文章の得意なモデル、と使い分けを試す |

### 4-A 例を見せる意味

ご指摘のとおり、アイデアは無限にあり、数例で網羅することはできない。例の目的は網羅ではなく、次の3つを示すことにある。

- **出力の書き方：** 仕組みカードの欄の埋め方。小さなモデルは、形式を例から学ぶと安定する。
- **境界：** 鍵の物を使う案は不受理、ゲームへの宣言は無視、あいまいなら確認、という線引き。
- **型の幅：** 作用の種類ごとに1つずつ。アイデアの数は無限でも、作用の種類は約10個なので、型の例なら足りる。

逆効果の心配もある。例に似た案ばかり受理し、例と違う案を誤解することがありうる。そこで次の3つで対処する。

- 例は「型の例」だと明記する。
- 例の中身は、ゲームの題材とずらした架空の物にする。
- 例ありと例なしで判定試験を回し、効果を数字で確かめる。効果がなければやめる。

将来は、試遊で集めた入力から、今の入力に近い例を選んで見せる方式も検討する。

### 4-B 必要十分な文脈の束

ご指摘のとおり、07・30・48のように、最初から全体のつじつまが必要なゲームでは、送る量を削りすぎると矛盾の原因になる。そこで方針を「最小」から「必要十分」へ改める。

各ゲームは、呼び出しの種類ごとに「文脈の束」を定義する。

| 束の中身 | 内容 | 削ってよいか |
|---|---|---|
| 固定事実 | その役割が知ってよい範囲の真相・設定 | 削らない |
| 確定事項 | これまでに確定した状態と、人物が話して事実になった内容（例：鏡が「袋は私の右の扉へ」と言った） | 削らない |
| 成果物 | 脚本や噺の本文など、作っている物の全文 | 削らない |
| 直近の会話 | 直前の数往復の原文 | 古い分は確定事項へ要約して置き換える |
| 飾り | 雑談や、確定事項に影響しない発言 | 削る |

人物が話した内容のうち、後で矛盾すると困るものは、ルール側で「確定事項」として記録し、次の呼び出しから必ず渡す。これで、長いゲームでもつじつまの根拠が失われない。無料枠の消費は増えるので、消費量は試験で測る。

## 5. 品質を確かめる仕組み

- **判定試験：** 言い方を変えた入力と、期待する判定の組をゲームごとに用意する。説明文やモデルを変えるたびに回す。無料枠を使うので、回数と消費を表示してから実行する。
- **講評の試験：** 同じ記録で3回作り、事実の誤り0件、3人の取り上げる出来事の違い、読みやすさを確認する。
- **試遊の記録から学ぶ：** 誤解された入力を集め、例（4-2）と誤解の表（1-3）に足していく。
- **無料枠切れ（ユーザー指定）：** 簡易モードは作らない。無料枠が切れたらプレイ不可とし、専用の画面を出す。
  - **開始前の確認：** 今日の残りの目安が、1プレイの予想消費の1.5倍に満たなければ、新しいプレイを始めない。
  - **プレイ中に切れた場合：** 状態を変えずに一時停止し、専用画面に切り替える。続きは枠が戻った後に再開できるようにする（中断保存の仕組みが必要）。
  - **専用画面の内容：** 枠が戻る時刻（Cloudflareの無料枠は毎日UTC 0時＝日本時間9時に戻る見込み。要確認）を示す。
  - キーワード処理は、AIの解釈との突き合わせ（1-4）にだけ使う。

## 6. ゲームの定義に追加する項目

詳細定義書§1の共通テンプレートに、次の項目を足す。

**AIに関わる定義（コードでは共通の `AiDefinition`。各ゲームはデータだけを書く）**

| 項目 | 内容 | コード上の欄 |
|---|---|---|
| 印の語彙 | ルールが知っている印、台詞での言い方、同じ意味の言葉 | `marks` |
| 自然な物の一覧 | 自然な物・鍵・法則に反する物 | `natural` |
| AIに任せる範囲 | 自由（味付け）・見立て・自然な物・型の中の誤解・禁止 の5区分ごとに、何を任せるか | `delegation` |
| 見立てを許すか | 許す／許さない | `appraisal.allowed` |
| 見立ての対象の種類 | 物・人物・場所など | `appraisal.subjectKinds` |
| 見立てに渡す公開説明 | 対象ごとの名前と見た目の説明。正解（大切かどうか等）は含めない | 各ゲームの対象データ（31は `description`） |
| 確認文のひな型 | 対象が空のとき／知らない基準を見立てられないとき／見立ての根拠がないとき。`{mark}` と `{examples}` を差し込む | `confirm` |
| 誤解の表 | 誤解の型と例。表にない誤解も、型に収まれば可 | `misreadings` |
| 作用の型 | 1-A の仕組みカード（条件→作用→費用） | （コード化は今後） |

**その他の定義**

1. 創作系の判定チェックリスト（2-4）
2. 講評の材料の選び方と割り当て（3-1、3-2）
3. 人物カードとネタ帳（3-3、3-4）
4. 判定試験のデータ（入力・期待する判定・はっきりした見立ての正解）。試験の実行部品は共通

### 6-A AIに任せる範囲の5区分

| 区分 | 任せ方 | 31の例 |
|---|---|---|
| 自由（味付け） | 台詞・描写・反応 | ピカリの台詞と、片付けの様子 |
| 見立て | プレイヤーが決めたあいまいな基準を、公開説明に当てはめる（はい・いいえ＋理由） | 「ママが好きそう」「キラキラした」 |
| 自然な物 | 補完してよいか、普通の性質 | 箱・机・ノート・ティッシュ |
| 型の中の誤解 | 誤解の表を基本に、型（条件→作用→費用）に収まる誤解 | 「持ち主」→物本人に面談 |
| 禁止 | AIに決めさせない | 本番の部屋の正解、達成、点数とランク |

### 6-B 見立ての仕組み（共通）

1. ルールが知らない基準（例：ママが好きそう）を受け取ったら、ゲームのルールは状態を変えずに「見立てが必要」と返す。
2. 共通の処理が、基準ごとに1回AIへ聞く。その基準について、まだ決まっていない対象は全部まとめて聞く。
3. 答えの理由が、その対象の公開説明の言葉を含まない場合は記録せず、ひな型の確認文で聞き返す。
4. 合格した答えを状態に記録する。同じ基準と対象の組には二度と聞かない。採点し直しても変わらない。
5. ルールが、記録を事実として使って判定する。結果画面と失敗理由に「〇〇の見立て」として表示する。

正解・真相・達成条件・点数は、引き続きルールだけが持つ。

## 7. 10本の中で注意が必要なゲーム

| ゲーム | 無料AIで難しい点 | 対策 |
|---|---|---|
| 07 鏡だけが目撃者 | 秘密を持つ人物との会話。人物の取り違えが起きやすい | 人物ごとに「話してよい事実の一覧」をルールで渡し、AIはその範囲の言い換えだけを行う |
| 30 誰も悪くない悪役脚本 | 創作の質の判定 | 4場面の枠と、チェックリスト判定（2-4） |
| 48 オチを先読みする落語星人 | 予想の生成と外れの判定 | 予想を「誰が／何を／どうなる」の選択式にし、比較はルールで行う |

逆に、31・01・13・19・37は、状態とルールで判定しやすく、無料AIとの相性がよい。制作順はこの相性を考慮する。

## 8. 計画への反映

[AI接続の計画](ai-connection-plan.md)の本命の接続先を、Cloudflare Workers AI（Gemma）に変える。本人のPlus枠（Luna）は、本人ローカルでの品質比較の基準として、同じ判定試験を回すときだけ使う。Gemmaの試験には、Cloudflareの新しいAPIトークン（本人が作成し、ローカルの設定ファイルに保存）が必要。
