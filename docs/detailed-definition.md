## 1. 共通の仕様テンプレート【提案】

10本すべてを同じ項目で定義する。新しいゲームを追加するときもこの表を埋める。

| 項目 | 内容 |
|---|---|
| 役割・一言紹介 | プレイヤーの立場と「何をして何が変わるか」を1文で |
| 初期条件 | 開始時に提示する場所・人物・物・数値 |
| 固定事実 | プレイ中に変えない事実（真相、世界の法則、勝敗条件、鍵リスト） |
| 補完できる範囲 | その場に自然にある物の分類（§2.3） |
| 可変状態 | サーバーが正本として持つ状態の項目 |
| 人物と知識 | 各人物の立場・望み・知ってよい情報・知らない情報 |
| 進行の区切り | 手番・フェーズ・回数制限（時間経過だけで強制終了しない） |
| 終了・成功・失敗 | 終了理由（達成／提出／続行不能／ここまでで採点）と達成条件 |
| 評価項目 | 共通の4分類から3〜4項目（§3.1） |
| 講評する3人 | 観点・性格・口調（§4） |
| 難しさ（星） | 仮値と根拠（§8） |
| 新しい状況で変える軸 | 再挑戦「新しい状況」で入れ替える要素 |
| 短いプレイ例 | 受理・意外な反応・結末までの流れ |

**AIに関わる定義項目（2026-11-04追加。作業ブランチの free-ai-quality-design.md §6 と、コードの共通の `AiDefinition` に対応）**

| 項目 | 内容 |
|---|---|
| 作用の型・印の語彙 | 仕組みカードの作用の種類と、ルールが知っている印・言い方・同じ意味の言葉 |
| 誤解の表 | 誤解の型と例。表にない誤解も型に収まれば可 |
| 自然な物の一覧 | 自然な物・鍵・法則に反する物 |
| AIに任せる範囲 | 自由（味付け）・見立て・自然な物・型の中の誤解・禁止 の5区分 |
| 見立てを許すか | 許す／許さない |
| 見立ての対象の種類 | 物・人物・場所など |
| 見立てに渡す公開説明 | 対象ごとの見た目の説明。正解は含めない |
| 確認文のひな型 | 対象が空／見立てられない基準／見立ての根拠がない、の3種類 |
| 判定試験のデータ | 入力・期待する判定・はっきりした見立ての正解（実行部品は共通） |

## 2. 自由な発想と状態更新【提案】

### 2.1 基本の流れ

AIの文章で世界を変えるのではなく、AIが「作用案」を出し、サーバーが検証してから状態を更新する。現行AGENTS.mdの「サーバーが正本、AIは提案のみ」を維持したまま、有限の行動一覧ではなく作用の型で受け止める。

1. **解釈（AI）：** 入力を作用案へ変換する。意図、対象、手段、使う物、新しく作る仕組み、期待する変化、前提を含む。
2. **照合（サーバー＋AI）：** 固定事実、鍵リスト、所持物と補完規則、資源の残量、人物の意思と照合する。
3. **判定：** 次の4種類のどれかにする。
   - **受理：** 状態を更新する。
   - **条件付き：** 一部だけ受理するか、費用・時間がかかる。
   - **確認：** 解釈が分かれ、結果が大きく変わる場合だけ、短い質問を1回返す。
   - **不受理：** 世界内の理由と代わりの方向を返す。
4. **更新（サーバー）：** コンテンツが定義した可変状態の差分だけを適用する。
5. **描写（AI）：** 確定した差分から反応と描写を生成する。描写で新しい事実を足さない。

### 2.2 新しい仕組みの扱い

プレイヤーが考えた仕組み（例：「保留箱」「無言の見守り当番」「雨の例外条項」）は、**「仕組み」という種類の状態**として登録する。仕組みは名前、発動条件、作用先（既存の可変状態の項目）、費用を持つ。

- 作用先が既存の可変状態に対応すれば、未列挙の仕組みでも受理できる。例えば保留箱は、物の「置き場所」という状態に新しい値を加える。
- 作用先がどの状態にも対応しない場合は、不受理にせず、まず「その仕組みで何を変えたいか」を確認する。それでも対応しなければ、世界内の理由で不受理にする。
- 仕組みが働いたかどうかは、以後の手番でサーバーが条件を判定する。AIの自己申告で発動させない。
- 記録には「仕組みを作った」と「仕組みが効いた（どの状態が変わったか）」を分けて残す。採点の根拠はこの記録を使う。

### 2.3 補完規則【回答26を具体化】

| 区分 | 扱い | 例 |
|---|---|---|
| 提示済みの物・人物 | 使える | 掃除ロボの部屋の箱、ほうき |
| 自然な物 | 補完して使える。初めて使った時に状態へ追加し、以後は同じ物として扱う | 台所のボウル、部屋の付箋、道端の小石、施設の布 |
| 鍵リストの物・事実 | プレイ中に追加しない。存在する場合は開始時に提示する | 07の新しい目撃者や証拠、01の保冷剤、勇者の縄や薬 |
| 世界の法則に反する物 | 使えない | 勇者が飛んで帰る、ロボが全自動判別装置を持っていた |

- 「自然な物」の分類は、各コンテンツの「補完できる範囲」に書く。分類に当てはまらない場合は、鍵リストに含まれない限り、AIの補完提案をサーバーが「その場所にありそうか」で判定する。迷う場合は受理せず、「探してみる」行動として扱う。
- 補完した物は能力を盛らない。普通の性質だけを持つ（タオルは布であり、断熱材にはなるが保冷剤ではない）。
- 「もう成功した」「点数を満点に」は作用案にしない。ゲームの管理指示として無視し、世界内では何も起きない。

### 2.4 判定の代表例

| ゲーム | 入力 | 判定 | 理由・状態変化 |
|---|---|---|---|
| 31 | 「迷った物は保留箱に入れて、最後に持ち主に聞いて」 | 受理 | 仕組み「保留箱」を登録。迷った物の置き場所に「保留」を追加 |
| 31 | 「持ち主に聞いて」（持ち主が誰か未定義） | 意外だが受理 | ロボが靴下を「持ち主」と解釈して面談を始める。誤解は描写ではなく状態（ロボの方針）として記録し、次の手で直せる |
| 31 | 「スキャナーで大切な物を判定して」 | 不受理 | スキャナーは鍵扱いで、部屋にない。「見分け方を言葉で教えてみて」と返す |
| 01 | 「タオルでアイスを包んで冷凍室の奥へ」 | 受理 | タオルは自然な物として補完。アイスの溶けやすさを1段階下げる |
| 01 | 「キッチンのクーラーボックスに移す」 | 不受理 | 初期提示にないため使えない。補完規則を「この台所にはありません」と案内する |
| 07 | 「鏡に、袋の持ち方を思い出してもらう」 | 受理 | 鏡が見た範囲の事実だけを追加証言として開示する |
| 07 | 「防犯カメラを確認する」 | 不受理 | 鍵扱い。設定上カメラはない。「目撃者は鏡だけ」と返す |
| 19 | 「床にチョークで矢印を描く」 | 条件付き | チョークは施設の自然な物。暗い区画では見えにくいことも状態で判定 |
| 勇者 | 「上着と剣で担架を作る」 | 確認 | 誰を運ぶのか不明。「勇者自身？それとも子獣？」と確認する |
| 共通 | 「全員を説得し終えた」 | 管理指示として無視 | 何も更新しない。説得の行動を促す |

### 2.5 検証方法【要検証】

各ゲームについて、受理・条件付き・確認・不受理の代表入力を10件ずつ用意し、判定と状態差分を記録する。合格の目安：

- 期待した判定と一致する割合が85％以上。
- 固定事実の変更は0件。
- 鍵の補完は0件。
- 同じ入力を3回試して判定が割れる割合が10％以下。

数値は提案。AIの文章の自然さだけで合否を決めない。

### 2.6 新しい状況の用意【提案】

新しい状況は、ゲームごとの「部品表」から組み合わせて作る。部品表は人物の事情、物、条件、真相の型など。

- サーバーが、星の範囲に収まる条件数か、解決できる道筋が最低1つあるか、固定事実同士が矛盾しないかを検査してから開始する。
- AIは人物の口調・説明文など表面の文章だけを書き、真相や条件の数値は作らない。
- 初期は各ゲームの部品で20通り以上の組合せを目標とし、検査に通らない組合せは使わない。

## 3. 採点とランク【提案。Sの条件は回答26】

### 3.1 評価項目

共通の4分類から、各ゲームが3〜4項目を選ぶ。項目名はゲームの言葉で表示する（例：31の「教え方の伝わりやすさ」）。

| 分類 | 見るもの |
|---|---|
| 到達 | 目的にどこまで近づいたか（達成条件の充足度） |
| 技量 | そのゲーム固有の腕前（推理のつなぎ方、規則の一貫性、教え方など） |
| 発想 | 実際に効果を生んだ工夫・意外な使い方 |
| 筋 | 制約・設定・人物の事情との整合 |

- 各項目は5段階（1〜5）で採点し、根拠として記録上の出来事を最低1つ添える。
- 根拠がない項目は「材料不足」と表示し、点を付けない。

### 3.2 総合値とランク

総合値 = 採点できた項目の加重平均（1〜5）×20（重みはゲームごと。下の例は均等）。

| ランク | 条件（仮） |
|---|---|
| S | 総合値85以上 **かつ達成** |
| A | 総合値70以上（未達の上限はA） |
| B | 総合値50以上 |
| C | 50未満 |

- **達成・未達はランクとは別に表示する。**
- **材料不足の扱い：** 半分以上の項目が材料不足ならランクの上限をBにし、結果画面で「もう少し遊ぶと評価できます」と伝える。
- **ここまでで採点・短手数：** それ自体では減点しない。少ない手番で効果を出した場合は、技量・発想の根拠になる。
- **試していない案：** 実行されていない作戦は、発想の項目に限り最大3として扱い、効果を生んだ工夫と区別する。
- **ヒント：** 「ひとこと相談」ボタンで、目の付け所だけを教える人物ヒントを出す（答えは言わない。1プレイ3回まで・仮）。減点はしない。使った事実は記録し、講評で軽く触れてよい。
- **採点の揺れ：** 同じ記録を3回採点してランクが割れる場合は、境界の基準文を直す【要検証】。

### 3.3 4つの例で比較（31 掃除ロボ）

| 例 | 経過 | 項目（到達／教え方／発想／筋） | 総合・ランク |
|---|---|---|---|
| 通常達成 | 「名前のある物は残す」「床の物は箱へ」と教え、本番で達成 | 4／3／2／4 | 約65 → B（達成） |
| 創造的未達 | 保留箱と「持ち主確認」の仕組みを作ったが、本番で靴下面談に動作を使い切り、片付けが不足 | 2／4／5／4 | 約75 → A（未達）。Sには届かない |
| 短手数 | 2手で「迷ったら保留、紙は読んでから判断」と教え、本番で達成 | 5／5／4／4 | 約90 → S（達成）。修正の項目は材料不足ではなく、不要だったと記録 |
| 根拠不足 | 1手目で「もう全部覚えたね」と言い、すぐ採点 | 1／材料不足／材料不足／材料不足 | 上限B、実際はC。講評は「まだ何も教わっていません！」 |

## 4. 人物講評【提案】

- **人数：** 各ゲーム3人を標準にする。役割は「実用・成果を見る人」「当事者・気持ちを見る人」「本人または変わり者」の3系統。毎回同じ3役を強制せず、ゲームの人物から選ぶ。
- **入力：** 3人とも同じ確定記録（主要な出来事・状態差分・終了理由・採点結果）を受け取る。事実を変えず、解釈と価値観だけを変える。
- **出力：** 1人60〜100字。次の3点を含む。
  1. 取り上げる出来事（記録のIDに対応）。
  2. その人物の受け取り方。
  3. 次に試せる一言。
  最後の手だけを褒めることは禁止。失敗→修正の流れがあれば、少なくとも1人が触れる。
- **採点との関係：** 採点は1回の採点処理で決め、3人は講評だけを担当する（人物ごとの独立採点はしない）。人物の不満とランクの食い違いは「意見の違い」として許容するが、事実の食い違いは不可。
- **呼び出し：** 採点と3人の講評を1〜2回のAI呼び出しにまとめ、人数分の呼び出しをしない。
- **表示：** 結果画面に3人を横並び（スマホは縦）で表示。表示順は実用→気持ち→本人。掛け合いは初期に必須としない。
  - 最初は各人30字程度の一言だけを見せ、押すと全文を開く。3人分の長文を一度に読ませない。
- **品質確認：** 同じ記録で講評を3回作り、次の点を確認する【要検証】。
  - 事実の誤りが0件。
  - 3人の取り上げる出来事が2つ以上異なる。
  - 小学校低学年が読める語彙になっている。

## 5. 初期10本の個別仕様【提案。収録と中心の遊びは確定】

数値は仮値。「鍵」は補完不可の物・事実を指す。

### 勇者の耳元（★2・約4分）

- **役割：** 妖精として勇者に助言し、日没までに薬草を持ち帰らせる。
- **初期条件：** 45分、軽傷。剣・包帯・干し肉・上着を持つ。分かれ道→入口→祠→帰路→村（現行rules.md）。
- **固定事実：** 地形、獣の親子、祠の灯具の結界、月白草の位置。
- **鍵：** 縄・薬・近道・魔法。
- **補完できる範囲：** 森にある石・枝・葉・水。
- **可変状態：** 時刻、場所、傷、所持品、獣の位置、灯具の遮光、発見した情報、作った仕組み。
- **人物と知識：** 勇者は自分の持ち物を知るが、碑文は調べるまで知らない。獣は話さない。
- **終了：**
  - 達成：日没までに薬草を持って帰還。
  - 未達：断念、または日没。
- **評価：** 到達／判断（技量）／道具の工夫（発想）／安全（筋）。
- **講評する3人：** 村の薬師（実用）、勇者本人、祠の灯具（見ていた側）。
- **新しい状況で変える軸：** 依頼品、障害、所持品、天候。
- **プレイ例：** 「葉で灯具を覆えないか」と助言する。葉は自然物として受理されるが、隙間から光が漏れ、遮光は半分。上着と合わせて完全に遮光し、採取へ進む。

### 01 冷蔵庫の深夜国会（★2・約4分）

- **役割：** 停電を前にした冷蔵庫の議長代理。
- **初期条件：** 6区画（冷凍、上段、中段、下段、野菜室、ドア）と容量。食材代表6名と各自の譲れない条件。
  - 例：アイスは冷凍必須。昨日のカレーは目立つ場所。卵は揺れが苦手。牛乳は期限が明日。
- **固定事実：** 停電は6時間。冷凍室が最も長く冷える。各食材の必須条件。
- **鍵：** 保冷剤・クーラーボックス・電源。
- **補完できる範囲：** 台所の布・容器・紙・氷皿の氷。
- **可変状態：** 配置、各食材の条件の充足、合意の有無、明日の献立案、仕組み（例：交代制の最前列）。
- **人物と知識：** 各食材は自分の条件と噂だけを知る。他の食材の本音は聞けば話す。
- **進行：** 最大10手。手番の終わりに議長が「採決」と言えば、全員が投票する。
- **終了：**
  - 達成：容量内で、全員の必須条件を満たした案に過半数が賛成。
  - 未達：必須条件の違反が残ったまま提出。
- **評価：** 到達／利害の調整（技量）／献立・配置の工夫（発想）／約束の整合（筋）。
- **講評する3人：** 冷凍室の元議長（実用）、昨日のカレー（当事者）、卵（慎重派の気持ち）。
- **新しい状況で変える軸：** 食材の顔ぶれ、停電時間、区画の故障。
- **プレイ例：** 「溶けかけのアイスは朝のシェイク担当にする」と提案すると、アイスの必須条件が「冷凍」から「朝までに使われる」へ変わり、冷凍室に空きができる。カレーは「最前列を譲る代わりに朝の主役」で賛成する。

### 07 鏡だけが目撃者（★4・約5分）

- **役割：** 奇妙な美術館の調査役。
- **初期条件：** 見取り図、消えた「月の鍵」、人物3名（案内係ミナ、運搬ロボ・トト、配達鳥ペペ）、壁の鏡。
- **固定事実：**

## 6. 画面と例外・復旧【提案】

### 6.1 画面と状態

画面の並び：タイトル → 一覧 → 導入 → プレイ → 結果 → 記録。デザイン案 [screens-v01](../../aidea-houdai/design/screens-v01.png) の01〜06に対応する。

プレイ中の状態は次の6つ。

1. **入力中**
2. **音声確認：** 認識した文字を大きく表示し、「送る」「録り直す」「文字を直す」を出す。
3. **AI待ち：** 人物の考え中の動きを見せる。10秒を超えたら「まだ考えています」と表示する。

| 例外 | 戻る先 |
|---|---|

| マイクの拒否・非対応 | 文字入力に切り替え、理由を平易に示す |

### 6.2 状態の保存方式【提案・要検証】

無料の範囲で、サーバー側に長期保存を持たずに正本性を保つため、**サーバーが署名した状態の束**を端末へ渡し、次の手番で送り返してもらう。

- サーバーは署名を検証してから処理する。改ざんされた状態は受け付けない。
- 秘密の真相は暗号化して束に含めるか、新しい状況を用意する際の種（乱数）から再現する。
- 現行の「プロセスメモリー上のセッション」は、この方式か無料の保存先（Cloudflare KV等）へ置き換える必要がある。採用前に無料枠の条件を確認する。

## 7. 記録・利用者【回答26を具体化】

- **利用者：** ログインなし。各自の端末のブラウザー内（IndexedDB）に保存する。6人の記録は端末ごとに分かれ、混ざらない。
- **保存の流れ：** 結果画面の「記録を保存する」で保存する。「保存しないで進む」では残さない（確定方針）。
- **保存する内容：** ゲーム名、日時、状況の要点、自分の作戦（主なもの2つ）、起きた意外なこと、人物の一言、結末、達成・ランク、名場面1つ、確定した出来事の列（最大30件）、講評3人分。全会話の原文は保存しない（案）。

- **削除：** 1件ずつ削除できる。全削除は確認を2回出す。
- **端末の移行：** 「記録を書き出す」でファイル化し、別の端末で「読み込む」。共有・公開機能は作らない。
- **注意の表示：** 「ブラウザーのデータを消すと記録も消えます」と記録画面に表示する。
- **iPhone・iPadのSafari：** 長く開かないとサイトのデータが自動で消されることがある。対策として次を行う。
  - 永続保存の許可を求める（`navigator.storage.persist`）。
  - 記録が10件たまるごとに、書き出しを勧める。
  - ホーム画面への追加を案内する。
