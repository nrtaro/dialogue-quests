# 本物のAI接続：完了までの全体像

2026-11-04 / Claude Code。対象は掃除ロボ（31）。ユーザーが「AI接続を優先」と決定。

> **更新（回答27）：** 無料AIのみで実装する目標になった。本命の接続先はCloudflare Workers AI（Gemma）。Plus枠（Luna）は本人ローカルでの品質比較の基準としてのみ使う。下の段階A〜Eは、接続先をGemma中心に読み替え、[free-ai-quality-design.md](free-ai-quality-design.md)の工夫を段階B〜Cに組み込む。

## 完了の定義

次の状態になったら「AI接続は完了」とする。

1. **接続：** あなたのPC上で、あなたのPlus枠（gpt-6-luna）を使い、掃除ロボを最初から最後まで遊べる。
   - 入力の解釈と3人の講評をAIが行う。
   - 採点の数値は、これまでどおりルール側で計算する。
2. **品質：** 判定試験（詳細定義§2.5）の基準を満たす。満たせない場合は、どこが足りないかが数字で分かっている。
3. **失敗への備え：** 次の場合に、状態を壊さず復帰できる。
   - 枠切れ
   - 認証の期限切れ
   - 通信の途中切断
   - 形式の誤り
4. **計測：** 1プレイの呼び出し回数・トークン・待ち時間を測り、費用と提供方法の判断に使える報告がある。

**範囲外：** 6人への遠隔提供、公開・デプロイ、音声入力、他の9本。

## 公式資料と既存の検証から分かっていること

| 事実 | 影響 |
|---|---|
| Plus枠の経路は `POST /v1/responses` に、OAuthのアクセストークンを付けて送る | ゲームの既存の「通常APIキー方式」とは別の接続部品が必要 |
| **`stream: true` と `store: false` が必須**。成功は `response.completed` を受け取った時だけ | 今のゲーム側の呼び出し（ストリーミングなし）は使えない。検証用スクリプトの受信処理を流用できる |
| **`max_output_tokens`、`temperature` などは送れない**。system役のメッセージも不可 | 今のゲーム側の呼び出しは `max_output_tokens` を送っているため、そのままでは失敗する |
| 会話の続きは毎回 `input` に履歴を入れて送る | 今の方式（履歴を毎回送る）と同じ |
| 枠切れは、ストリームの途中で `subscription_sharing_usage_limit_exceeded` / `_unavailable` として届く | 「枠切れ」として見分け、状態を変えずに一時停止させる |
| `offline_access` で更新用トークンを受け取れる。アクセストークンは1時間程度 | 更新の処理と、端末内の保護された保存が必要。毎回ログインし直さない |
| リダイレクト先は `http://127.0.0.1:<ポート>/auth/callback`。ポート以外は変更不可 | ゲームのサーバーに `/auth/callback` を用意すれば、既存の登録（client ID）を再利用できる |
| JSONスキーマによる構造化出力は、公式資料に明記がない。ただし検証では正常に動いた | 形式の誤りに備えて、受け取った側でも検証を続ける |
| 既存の検証で gpt-6-luna への短い推論が 2,080ms で成功（168トークン） | 接続そのものは成立している。ゲームの長い入力での速度・量は未知 |

## 段階と順序

### A. 接続の部品（ゲームサーバー側）

1. **ログイン：**
   - `/api/auth/chatgpt/login` と `/auth/callback` を追加する（PKCE、state、nonce、IDトークンの署名検証は検証用スクリプトの実装を移植）。
   - 開発サーバーが `127.0.0.1` のときだけ有効にする。
2. **認証情報の保存と更新：**
   - Gitの対象外にある `play-logs/` に、本人専用で保存する。ログには出さない。
   - 期限前に更新用トークンで更新する。更新の手順は、公式のトークン資料で確認してから実装する（**未確認の要素**）。
3. **AIの呼び出し部品（`PlanProvider`）：**
   - ストリーミングを受信し、`response.completed` だけを成功とする。
   - 送れない項目は除外する。
   - 呼び出しの種類は、解釈（`interpret`）と講評の2つ。
4. **失敗の扱い：**
   - 枠切れ → 状態を変えずに「一時停止」と表示する。
   - 期限切れ → 自動で更新し、失敗したら再ログインを案内する。
   - 途中切断・形式の誤り → 入力を残したまま再試行できる。
5. **切替：** `AI_PROVIDER=chatgpt-plan` で有効にする。通常API課金へは自動で切り替えない。

### B. 判定の品質（掃除ロボ）

6. **判定試験の台本：** 詳細定義§2.5の判定試験の台本を作る。
   - 受理・条件付き・確認・不受理の入力を各10件、言い方を変えて用意する。
   - それぞれ3回ずつAIに解釈させ、ルールの判定と比べる。
   - 呼び出しは約120回。あなたのPlus枠を消費するので、実行前に回数を表示して確認する。
7. **改善：** 結果を見て、AIへの説明文と「印」の語彙を直す。レビュー指摘R2（既存の状態に当てはまらない仕組み）の対応もここで行う。

### C. 講評をAIに任せる

8. **講評の生成：** 確定した記録（出来事・本番の結果・評価）だけを渡し、3人の講評を1回の呼び出しで作る。
   - 出てくる物の名前が記録にあるか、長さが範囲内かを検査する。
   - 失敗したら、今の定型の講評に戻す。
9. **品質確認：** 同じ記録で3回作り、事実の誤りがないか、3人の視点が違うかを確認する（詳細定義§4）。

### D. 計測と画面

10. **記録：** 呼び出しごとにトークン数と待ち時間を `play-logs/` に記録する。
11. **画面：** 接続状態、ログインボタン、AIの考え中表示、枠切れ時の一時停止を出す。
12. **試遊と計測：** 5回通して遊び、1プレイあたりの呼び出し回数・トークン数・待ち時間の合計を出す。

### E. 判断材料の報告

13. **報告：** 品質・速度・使用量をまとめる。そのうえで、少額課金（通常API）の場合の月額の試算と、Gemmaとの比較案を示す。
    - Gemmaの再試験には、新しい資格情報の作成にあなたの許可が必要。
    - 月の上限額と、1人1日のプレイ回数は、ここであなたに判断してもらう。

## リスクと対策

| リスク | 対策 |
|---|---|
| トークン更新の手順が資料に書かれていない | Aの最初に、公式のトークン資料を確認する。分からなければ、当面は「期限が切れたら再ログイン」で進める |
| Plus枠の上限が公開されていない | 枠切れを正しく見分けて止める。計測で、実際に何回遊べたかを記録する |
| プレビュー機能の仕様が変わる | 接続の部品を1か所にまとめ、ゲームのルール側に影響させない |
| 長い入力で待ち時間が延びる | 履歴を短くし（直近の会話と状態の要約）、AIへ送る量を測る |
| AIの解釈が揺れる | ルール側の判定は変えず、判定試験の数字で改善を追う |

## あなたに確認が必要な場面

- **Aの完了後：** ブラウザーで、OpenAIの許可画面を確認してもらう（既存の登録を再利用できれば、確認だけで済む見込み）。
- **Bの実行前：** 約120回の呼び出しでPlus枠を使ってよいか。
- **Eの報告後：** 少額課金の上限額、1日のプレイ回数、Gemmaの再試験をするか。
