# 開発・修正方針（AIデア放題！）

## 1. 基本方針

- AIデア放題！は、生成AIで多様なミニゲームやシチュエーションを遊ぶプラットフォームです。
- 日常、ファンタジー、SF、推理、コメディ、討論など、ジャンルもゲーム形式も違うコンテンツを追加していく前提で作ります。
- 「勇者の耳元」は、遊びながら仕組み・UI・UX・AIの挙動・バランスを磨くためのデモです。プロジェクトの中心ではありません。
- 目的は、勇者の耳元を完成させることではありません。次のコンテンツでも再利用できる基盤を整えることです。

## 2. 最重要原則：まず汎用性を考える

勇者の耳元で問題を見つけたら、勇者専用のルールや例外で塞ぐ前に、次の5つを確認します。

1. この問題は他のゲームでも起こり得るか。
2. 原因は共通システムにあるか、コンテンツ固有の仕様にあるか。
3. 共通システムを直せば、他のゲームも含めて改善できるか。
4. 新しいゲームを足したとき、同じ対応を繰り返さずに済むか。
5. その修正が、別ジャンルのゲームに不要な制約を課さないか。

例：AIの応答が長くてテンポが悪い場合
- 勇者専用の文字数制限を足すだけで終わらせない。
- ゲームごとに応答量とテンポを設定できる共通の仕組みを検討する。現在の `limits`（入力・語り・台詞の上限）がこの形です。

選択肢、進行、AI応答の解析、結果判定、UI表示も同じ考え方で扱います。

## 3. 共通基盤とコンテンツ固有要素の分け方

すべてを1つの仕組みに統一する必要はありません。共通にすべき所は共通にし、固有であるべき所は独立させます。

| 区分 | 主な内容 | 現在の主な置き場所 |
|---|---|---|
| 共通基盤 | 開始・進行・終了の管理、排他、二重送信防止 | `src/server/session.ts` |
| 共通基盤 | AIとの通信、応答処理、エラー処理、無料枠 | `src/server/ai.ts`・`workers-ai.ts`・`quota.ts`・`http.ts` |
| 共通基盤 | コンテンツの契約と登録 | `src/game/types.ts`・`src/content/registry.ts` |
| 共通基盤 | 共通UI（一覧・概要・プレイ・結果・枠切れ） | `src/components/*` |
| 共通基盤 | 遊び方の型ごとの共通エンジン | `src/game/trpg/*`（TRPG型）、`src/game/effects.ts`・`appraisal.ts`（作用案・見立て） |
| 共通基盤 | ログ、検証、品質確認 | 記録の出力、`scripts/*`、`tests/*` |
| コンテンツ固有 | 世界観、登場人物、シナリオ、勝敗条件、固有ルール、役割、演出、難易度、報酬 | `src/content/<コンテンツ>/`、`src/content/scenarios/*` |

この表は分類の目安です。実際の分担は、既存コードと次のコンテンツの要件を見て決めます。

**コンテンツ固有の値はデータとして渡します。** 共通コードは「どう扱うか」だけを持ちます。
- 例：道のりと時間はシナリオの `routes`、締切はシナリオの `clock`、ゴールの品はゴールの `gives` / `needs` で渡す。

## 4. 修正依頼を受けたときの手順

1. **問題の特定**：今の挙動、期待する挙動、起きる条件を整理する。
2. **影響範囲の分析**：
   - 共通基盤の問題か、コンテンツ固有の問題かを判定する。
   - 共通なら、どのゲームに影響するかを確かめる。
3. **修正方針の検討**：
   - 局所的な修正と汎用的な修正を比べる。
   - 再利用性、複雑さ、保守性、既存機能への影響で評価する。
   - 方針の選び方がユーザーの判断に関わるときは、実装前に確認する。
4. **実装**：
   - いちばん適切な範囲で直す。
   - その場しのぎのハードコード、例外処理の積み増し、不要な依存は避ける。
5. **検証**：
   - 勇者の耳元で動作を確かめる。
   - 共通部分の変更が、他のコンテンツ（掃除ロボ、テスト用の最小シナリオなど）を壊していないか確かめる。
   - まだ存在しないゲームへの適合性は「想定」として書き、確認済みの結果と分ける。

**報告と記録：** 修正内容は「共通システム」「コンテンツ固有」「要検証」に分けて報告し、`docs/progress.md` に残します（handoff.md §9と同じ分類）。

## 5. 避けること

- 勇者の耳元専用の条件分岐を、共通システムに増やし続ける。
- 特定のシナリオや登場人物を前提に、共通ロジックを設計する。
- コンテンツが増えるたびに、共通コードの大幅な書き換えが必要になる作りにする。
- ゲーム固有の設定値を、共通処理に直接書き込む。
- 共通基盤で解くべき問題を、ゲームごとに個別に直す。
- 将来の拡張を理由に、必要性がはっきりしない複雑な抽象化を先に作る。
- 汎用化を優先しすぎて、各ゲームの独自性や面白さを損なう。

## 6. 体験品質とゲームバランス

**共通の品質基準を持つもの：**
- テンポ（1手番の待ち時間、待つ間に何を見せるか）
- AI応答の自然さと長さ
- 操作の分かりやすさ（次に何をすればよいか分かるか）
- 画面構成（PC・スマホ、入力欄が隠れないこと）
- エラーからの復帰、リトライのしやすさ
- 無料枠を使い切ったときの案内

**コンテンツごとに決めるもの：**
- 難易度、勝敗条件、ゲームの長さ、選択の自由度、AIの振る舞い

**共通化するのは数値そのものではありません。** バランスを設定・検証・調整できる仕組みを共通にします。
- 設定：値はコンテンツ定義で上書きできるようにし、共通側には「既定値」だけを置く。
- 検証：自動プレイの台本（`scripts/trpg-play.ts` など）で、成功率の分布・所要時間・クリア率をコンテンツごとに測れるようにする。
- 調整：測った結果を見て、そのコンテンツの定義だけを変える。

違うジャンルのゲームを、無理に同じ体験へそろえません。

## 7. 現状とこの方針の差（2026-11-06 時点）

すぐに直すものではありません。関わる修正が来たときに、この方針で判断する対象として記録します。

- **共通エンジンに固定値が埋め込まれている：**
  - 成功率の調整値（持ち物＋2、無視した障害−3など）、1手番の移動距離、持ち物の上限8個は、共通コード `src/game/trpg/engine.ts` の固定値です。
  - シナリオで上書きできないので、§6の「既定値＋上書き」の形にする候補です。
- **コンテンツの型が3種類ある：** 決まった行動の表、作用案、TRPGが同居しています（`src/server/session.ts` の分岐）。どの型に寄せるかは、次のコンテンツを決めるときに判断します。
- **名称が古い：** `README.md` と `AGENTS.md` の表題は旧称「Dialogue Quests」のままです。名称の変更は別途ユーザーが判断します。
- **参照先がない：** `AGENTS.md` が根拠に挙げる企画文書 `detailed-definition.md` は、このリポジトリに入っていません（別のチェックアウトの `docs/` にだけあります）。
- **ルールの記録先が古い：** `AGENTS.md` は「ルールは docs/rules.md を更新」としています。ただし `rules.md` は旧方式（決まった行動の表）のルールで、TRPG型のルールは `docs/trpg-*.md` に書かれています。
